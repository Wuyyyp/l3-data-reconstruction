# Preflight Shared LoMa Cache

## Goal

Make clip preflight and formal LoMa matching share one process-level backend and GPU feature cache, while reusing sampled preflight pair results during the full match stage.

## Design

- `match-delivery` becomes the single owner of the preflight-to-matching lifecycle.
- It runs preflight first, using stable image-path keys and the configured LoMa GPU feature cache.
- It then runs all configured intra/inter matching in the same Python process. The module-level LoMa backend and GPU feature cache therefore remain alive across both phases.
- Pair results generated by preflight continue to be stored in `PreflightMatchCache`. Formal matching reuses those results and applies the current semantic masks before evaluation.
- The standalone delivery `preflight-quality` subprocess is removed from the default stage list to avoid running preflight in a different process and repeating it later.
- Cache diagnostics report hits and misses from both phases without changing match coordinates or filtering behavior.

## Non-goals

- No disk serialization of GPU tensors.
- No change to pair sampling, semantic mask policy, match filtering, or optimization parameters.
- No change to the persisted match-cache layout.

## Verification

- Unit test that preflight calls `run_match_backend` with stable image keys.
- Unit test that `match-delivery` invokes preflight before persistent matching in one process.
- Existing LoMa, preflight, staged-pipeline, and delivery-profile tests remain green.
